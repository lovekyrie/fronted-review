### 测试策略

高级前端面试里的测试题，重点不是“会不会写 `expect`”，而是：

- 你如何划分测试层次
- 你如何判断哪些值得测
- 你如何防止测试体系拖慢交付

更好的回答方式是把测试看成质量策略的一部分，而不是工具题。

#### 1. 为什么需要测试分层

不同类型的问题，应该由不同层级的测试去发现。

如果所有问题都指望 E2E：

- 成本高
- 反馈慢
- 失败难定位

如果所有问题都只靠单测：

- 很多集成问题覆盖不到
- UI 交互和真实浏览器行为会缺失

所以更合理的思路是分层。

#### 2. 常见测试层次

##### 2.1 单元测试

目标：

- 验证纯函数、工具函数、状态转换逻辑
- 快速反馈
- 低成本覆盖边界条件

适合：

- 工具函数
- reducer
- 数据转换函数
- 自定义 Hook 中不依赖真实 DOM 的部分

##### 2.2 组件测试

目标：

- 验证组件在接近真实使用方式下的表现
- 关注渲染、交互、状态变化、可访问性

适合：

- 表单组件
- 列表组件
- 弹窗
- 数据展示组件

重点不是测内部实现，而是测用户能看到和操作到的结果。

##### 2.3 集成测试

目标：

- 验证多个模块协作是否正常
- 检查组件、状态、请求层组合后的行为

适合：

- 页面级交互
- 表单提交流程
- 路由切换后的联动逻辑

##### 2.4 E2E 测试

目标：

- 从用户视角验证关键业务流程
- 发现真实浏览器环境里的集成问题

适合：

- 登录
- 下单
- 搜索
- 支付前流程
- 权限跳转

E2E 不应该覆盖所有细枝末节，而应该覆盖最关键、最怕坏、跨层协作最复杂的主路径。

#### 3. 一个实用的测试金字塔

更稳的策略通常是：

- 大量单元测试
- 适量组件 / 集成测试
- 少量关键 E2E

这背后的原因不是教条，而是成本与反馈速度：

- 单测便宜且快
- 组件测试更接近真实使用
- E2E 最慢但最接近真实环境

#### 4. 什么值得测

不是所有代码都值得同样强度地测试。

更值得测的通常包括：

- 容易回归的逻辑
- 业务价值高的流程
- 状态组合复杂的模块
- 历史上出过事故的地方
- 外部依赖多、集成边界复杂的部分

不值得过度测试的通常包括：

- 纯静态展示且逻辑极少的页面
- 第三方库已经充分保证的内部行为
- 对实现细节绑定过深的断言

#### 5. 如何写“抗重构”的测试

好的测试应该更多关注行为，而不是实现细节。

错误方向：

- 测内部 state 变量
- 测私有方法是否被调用
- 测某个 hook 被调用几次

更稳的方向：

- 用户输入后页面如何变化
- 某个按钮是否可点击
- 错误提示是否出现
- 提交后是否发生正确请求

#### 6. Mock 的边界

Mock 是必要工具，但不能滥用。

##### 6.1 适合 Mock 的对象

- 网络请求
- 时间
- 浏览器 API
- 第三方 SDK

##### 6.2 不适合过度 Mock 的对象

- 你真正想验证的核心逻辑
- 组件之间的真实协作
- 关键用户流程

过度 Mock 的后果是测试“全绿”，真实系统一跑就坏。

#### 7. 覆盖率怎么看

覆盖率是参考指标，不是目标本身。

高覆盖率不等于高质量，因为：

- 断言可能很弱
- 关键分支可能没测到
- 只执行到了代码，不代表验证到了行为

更好的说法是：

- 用覆盖率发现明显未覆盖区域
- 不把覆盖率当唯一 KPI
- 更关注高价值逻辑是否被有效断言

#### 8. Flaky Test 怎么处理

不稳定测试是测试体系最伤团队信任的地方之一。

常见原因：

- 依赖时间
- 依赖网络
- 依赖异步时机
- 依赖全局共享状态
- 依赖脆弱选择器

常见治理方式：

- 等待真实可见状态，而不是盲等时间
- 隔离测试数据
- 减少共享环境依赖
- 稳定定位器
- 对异步行为做更明确同步

#### 9. 前端项目里的推荐工具组合

##### 9.1 单测 / 组件测试

适合用：

- Vitest
- Testing Library / Vue Test Utils

##### 9.2 E2E

适合用：

- Playwright

这类组合的优势是：

- 反馈快
- 与现代前端构建工具兼容好
- 覆盖从函数到浏览器流程的不同层次

#### 10. CI 里怎么跑测试

测试策略要和交付链路配合，而不是单独存在。

一个更合理的 CI 思路通常是：

1. PR 阶段跑 lint、单测、组件测试、构建校验
2. 主干阶段增加关键 E2E 或冒烟测试
3. 发布后观察错误监控和关键指标

这样做的原因：

- 快反馈放前面
- 高成本验证放后面
- 不让整个团队被最慢测试拖住

#### 11. 如果这个仓库继续补测试，优先补什么

当前仓库更适合先补两类内容：

1. 手写实现的单元测试
2. 文档站或关键交互的最小冒烟测试

优先级最高的候选：

- `hand-write/promise`
- `hand-write/simulate/eventEmitter.js`
- 一些工具函数和状态转换逻辑

#### 12. 高频面试题

##### 12.1 单测、组件测试、E2E 怎么分工

单测负责小逻辑和边界，组件测试负责交互和渲染行为，E2E 负责关键业务路径和真实浏览器集成问题。

##### 12.2 为什么高覆盖率不等于高质量

因为覆盖率只能说明代码被执行过，不代表关键行为被正确验证，也不代表断言足够强。

##### 12.3 为什么测试要分层

因为不同层测试的反馈速度、成本和定位能力不同。把所有问题都压给某一层，都会导致质量体系失衡。

##### 12.4 什么是好的前端测试

能稳定发现高价值问题、反馈快、对重构友好、对实现细节耦合低、在团队里可维护。

#### 13. 面试回答建议

如果被问测试策略，不要只说“我们用 Vitest 和 Playwright”。更稳的结构是：

1. 先说为什么需要测试分层
2. 再说每层测什么、不测什么
3. 再说 mock、覆盖率、flaky 的取舍
4. 最后补 CI 如何承接测试策略

这样答案会从“会写测试”升级成“会设计质量保障体系”。
