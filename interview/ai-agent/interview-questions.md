# AI Agent 高频面试题

## 核心结论

AI Agent 面试不要停在概念解释，要把答案落到工程链路：输入如何组织，模型如何决策，工具如何执行，知识如何检索，状态如何保存，前端如何展示，失败如何恢复，效果如何评估。

答题模板可以统一成：

```text
先给结论 -> 拆工程链路 -> 讲关键取舍 -> 补风险兜底 -> 落到前端或项目
```

## 工程链路

```text
需求分析
  -> Prompt / Tool / RAG / Memory 选型
  -> Runtime 协议和前端交互设计
  -> 权限、错误、确认和审计
  -> 评估集、trace 和线上指标
```

## 关键概念

- Agent：能基于目标进行推理、选择工具并完成多步骤任务的系统。
- Tool：模型可调用的外部能力。
- MCP：标准化暴露和连接工具的协议思路。
- RAG：用检索补充私有知识和实时信息。
- Memory：跨轮次保存必要上下文和偏好。
- Runtime：让 Agent 可运行、可交互、可中断的任务层。
- Evaluation：用固定样本和线上指标判断质量。

## 常见坑点

- 把 Agent 说成“套壳聊天机器人”。
- 只强调模型能力，不讲工具权限和错误恢复。
- RAG 只讲向量库，不讲切分、召回、重排和评估。
- 不区分流式文本和结构化事件协议。
- 多 Agent 讲得很复杂，但说不出为什么要拆角色。

## 高频题与回答模板

### 1. 你怎么理解 AI Agent？

Agent 是围绕目标执行任务的系统，不只是生成文本。它通常包含模型推理、工具调用、上下文管理、任务状态和结果评估。模型负责理解和决策，工具负责访问外部系统，Memory 和 RAG 补充上下文，Runtime 负责流式交互、取消重试和人工确认。

如果落到前端项目，我会重点关注 Agent 过程如何展示给用户，比如工具调用卡片、引用来源、确认表单、错误恢复和任务回放。

### 2. Agent 和普通 Chatbot 有什么区别？

普通 Chatbot 主要回答问题，Agent 更强调执行任务。区别在于 Agent 会根据目标规划步骤，必要时调用工具或检索知识，并根据结果继续决策。工程上 Agent 需要权限控制、状态管理、工具审计和评估体系，而 Chatbot 更多是消息输入输出。

一句话概括：Chatbot 偏对话，Agent 偏任务执行。

### 3. Tool calling 怎么设计才稳定？

我会先把工具职责拆小，每个工具只做一个明确动作，然后定义参数 schema、返回结构、权限和错误码。模型只生成工具调用意图和参数，真正执行由应用运行时完成。对于写操作，要加人工确认、幂等 key 和审计日志。

稳定性的关键是：schema 清晰、参数可校验、结果可解析、失败可恢复。

### 4. MCP 解决什么问题？

MCP 解决工具和数据源连接标准化的问题。没有 MCP 时，每个 Agent 客户端都要单独适配文件系统、浏览器、数据库或内部平台。通过 MCP Server，可以把这些能力以统一协议暴露出来，客户端负责发现工具、读取资源和发起调用。

我会把 MCP 理解成 Agent 时代的工具连接层，它降低集成成本，但不替代权限、审计和业务安全设计。

### 5. RAG 的完整链路是什么？

RAG 链路是 Loader 读取数据，清洗后用 Splitter 切分 chunk，Embedding 生成向量并写入索引；用户提问时先做 query 处理，再用向量检索和 BM25 混合召回，必要时 reranker 重排，最后把高质量片段和来源引用交给模型生成答案。

工程上我会额外关注数据更新、权限过滤、引用准确性和评估集，避免只接向量库但答案不可验证。

### 6. 为什么 RAG 不能只靠向量检索？

向量检索擅长语义相似，但对 API 名、错误码、版本号、专有名词不一定稳定。前端知识库里很多问题需要精确命中，例如某个配置项、函数名或报错信息，所以通常会把向量召回和 BM25 关键词召回结合，再用 reranker 排序。

混合检索的目标是同时保证语义召回和精确召回。

### 7. Memory 应该怎么设计？

Memory 要按用途拆分。短期上下文适合最近几轮对话；摘要记忆适合长任务，保留目标、约束和进度；长期记忆适合稳定偏好或项目事实。不能把所有对话都自动写成长期记忆，否则容易污染和泄露隐私。

我会给 Memory 加写入规则、过期策略、用户可见和删除能力。

### 8. Output Parser 有什么价值？

Parser 的价值是让模型输出能稳定进入系统。比如前端需要渲染表单、步骤、评分或图节点，就不能只依赖自然语言。通过 JSON schema 或结构化格式，Parser 可以校验字段是否完整、类型是否正确、引用是否合法。

解析失败时可以触发自动修复、重试或降级，而不是把脏数据交给 UI。

### 9. SSE 在 Agent 前端里怎么用？

SSE 可以把 Agent 执行过程实时推给前端。事件不应该只有 token delta，还应该包含任务开始、工具调用开始和结束、引用片段、人工确认、错误和任务完成。前端根据事件渲染消息、工具卡片、进度和确认表单。

关键点是每个任务要有 runId，每个工具调用要有 toolCallId，并支持取消、重连和回放。

### 10. 什么时候需要 LangGraph 这类图编排？

当任务有多步骤、条件分支、循环重试、人工确认或多角色协作时，图编排比简单 Prompt 链更清晰。它把流程拆成节点和边，用共享状态记录任务进度，再通过条件边决定下一步。

如果只是简单问答，不需要引入复杂图；如果是“检索、执行、审查、确认、总结”的流程，图编排就很有价值。

### 11. 多 Agent 怎么拆才合理？

多 Agent 要按职责、工具权限或评估标准拆，而不是为了概念而拆。常见拆法是 Planner 负责任务拆解，Retriever 负责检索证据，Executor 负责工具执行，Reviewer 负责检查风险和正确性，Final Agent 负责组织最终回答。

拆分后要控制通信成本、最大步数和权限边界，否则多 Agent 会变慢且更难调试。

### 12. Agentic RAG 和普通 RAG 有什么区别？

普通 RAG 通常是一次检索后生成答案。Agentic RAG 会让 Agent 自己判断是否需要改写 query、多轮检索、调用工具验证或补充引用。它更适合复杂问题，但延迟和成本更高。

工程上要设置最大检索轮次、停止条件和评估指标，避免 Agent 一直反思和检索。

### 13. Agent 系统怎么做评估？

我会分成离线和线上。离线用固定评估集回放，看 RAG 的 Recall@K、引用准确率、答案正确率，以及 Agent 的任务完成率和工具成功率。线上记录 trace，包含 prompt、检索结果、工具调用、模型输出、耗时、成本和用户反馈。

这样出现问题时能定位到是检索失败、上下文拼接错误、工具异常、模型幻觉还是协议渲染问题。

### 14. Agent 为什么容易产生安全风险？

因为 Agent 不只是回答，还可能调用工具产生副作用。风险包括越权访问、错误写入、重复执行、敏感信息泄露、Prompt 注入和工具结果污染。解决思路是最小权限、参数校验、人工确认、幂等设计、审计日志和敏感信息脱敏。

高风险动作必须让用户确认关键参数和影响范围。

### 15. 前端工程师在 Agent 项目里能做什么？

前端不只是做聊天框。前端需要设计流式交互、工具调用卡片、引用展示、人工确认、任务取消、错误恢复、语音交互和运行记录。还可以参与 Prompt 输出协议、RAG 引用展示、评估面板和可观测性页面。

如果做得深入，前端其实是在搭 Agent 的产品运行时。

## 面试回答模板

> 我回答 Agent 题时会先定义边界：Agent 是能围绕目标做推理、调用工具并完成任务的系统。然后拆链路：Prompt 组织任务，Tool/MCP 连接外部能力，RAG 和 Memory 提供上下文，Runtime 用 SSE 或事件协议展示过程，最后通过 trace 和评估集持续优化。工程取舍上，我会特别关注工具权限、结构化输出、人工确认、错误恢复、延迟成本和评估指标，因为这些决定 Agent 能不能从 demo 走到真实项目。

## 后续实战方向

- 把以上 15 题录成 1-3 分钟口述稿，训练“结论、链路、取舍、风险、项目”的表达节奏。
- 为每题补一个项目例子，例如知识库问答、浏览器助手、面试模拟 Agent。
- 按 Tool、RAG、Runtime、Evaluation 四类整理追问清单。
