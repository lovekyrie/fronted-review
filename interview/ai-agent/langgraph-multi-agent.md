# LangGraph 与多 Agent

## 核心结论

当 Agent 任务从单轮问答升级到多步骤执行时，单纯 Prompt 链会变得难以维护。LangGraph 这类图编排思路把流程拆成节点、边、条件分支和共享状态，让规划、检索、工具执行、人工确认、审查和结束条件变得更清晰。

多 Agent 不是越多越好。只有当任务天然存在不同角色、不同工具权限或不同评估标准时，拆分多个 Agent 才有价值。

## 工程链路

```text
用户目标
  -> Planner 节点拆解任务
  -> Router 节点判断走检索、工具还是追问
  -> Retriever 节点召回知识
  -> Executor 节点调用工具
  -> Reviewer 节点检查结果和风险
  -> Human 节点处理确认或补充信息
  -> Final 节点生成答案
```

图编排关注三个问题：

- 当前状态是什么。
- 下一步应该去哪个节点。
- 什么时候结束、重试或交给人工。

## 关键概念

### State

State 是图里的共享任务状态，可以包含用户目标、已完成步骤、检索结果、工具结果、错误、用户确认和最终答案。它比“把所有消息塞进上下文”更适合复杂任务。

### Node

Node 是一个可执行步骤，例如规划、检索、调用工具、评估结果、生成回复。Node 的输入输出要明确，方便单独测试和替换。

### Edge

Edge 表示节点之间的流转关系。普通边是固定流程，条件边会根据状态选择下一步。例如工具失败后可以重试，信息不足时可以追问，风险高时进入人工确认。

### Planner / Executor

Planner 负责把目标拆成步骤，Executor 负责执行具体工具。把规划和执行拆开，可以降低模型一边想一边做导致的混乱，也便于在执行前插入权限和风险检查。

### Reviewer

Reviewer 负责检查答案是否满足要求、是否引用来源、是否遗漏约束、是否存在高风险动作。它可以是模型节点，也可以是规则校验。

### 多 Agent 协作

常见拆分方式：

- 规划 Agent：拆解任务和安排顺序。
- 检索 Agent：负责 RAG 查询和证据整理。
- 执行 Agent：调用工具完成动作。
- 审查 Agent：检查正确性、安全性和格式。
- 总结 Agent：面向用户生成最终表达。

### Agentic RAG

Agentic RAG 不是一次检索后直接回答，而是让 Agent 自己决定是否改写问题、是否多轮检索、是否调用工具验证、是否补充引用。它适合复杂问题，但成本和延迟更高，需要设置停止条件。

## 常见坑点

- 为了“多 Agent”而多 Agent，角色拆分没有实际收益。
- 图状态设计混乱，节点之间靠自然语言传递关键数据。
- 没有结束条件，Agent 在规划、检索和反思之间循环。
- Reviewer 只做语气润色，没有真正校验证据和约束。
- Planner 生成太细的步骤，执行成本过高。
- 多 Agent 共用高权限工具，无法做角色级权限控制。
- Agentic RAG 不限制检索轮次，延迟和成本不可控。

## 面试回答模板

> 我会在任务变成多步骤、需要条件分支或人工确认时引入图编排。核心是把流程拆成 Planner、Retriever、Executor、Reviewer、Human 和 Final 等节点，用共享 State 记录目标、工具结果、错误和确认状态，再用条件边控制重试、追问、结束和人工介入。多 Agent 只有在角色职责、工具权限或评估标准不同的时候才拆，否则会增加通信成本。对于 Agentic RAG，我会限制检索轮次和成本，并要求每次答案能回到证据来源。

## 后续实战方向

- 为“面试模拟 Agent”设计图状态：题目、回答、追问、评分、改进建议。
- 做一个 RAG Router：简单问题直接回答，复杂问题多轮检索和重排。
- 给高风险工具调用前插入 Reviewer 和 Human 节点。
- 设计最大步数、最大成本和最大重试次数，避免图执行失控。
