# 评估与观测

## 核心结论

Agent 系统上线后最难的不是“能不能回答”，而是“如何知道它回答得好不好，为什么变差，改动是否有效”。评估解决质量判断，观测解决过程还原，两者合起来才能支撑持续迭代。

面试里要把指标讲完整：RAG 看召回率和引用正确性，Agent 看任务完成率和工具成功率，Runtime 看延迟和错误率，业务看用户采纳率和人工介入率，成本看 token、模型、检索和重排消耗。

## 工程链路

```text
线上请求
  -> 记录 traceId、prompt、模型、参数
  -> 记录检索 query、召回文档、rerank 分数
  -> 记录工具调用、参数、耗时、错误
  -> 记录模型输出、引用、用户反馈
  -> 离线评估集回放
  -> 对比正确率、召回率、延迟、成本
  -> 调整 Prompt、检索、工具或模型
```

## 关键概念

### Trace

Trace 用来还原一次 Agent 运行过程。它应该覆盖用户输入、Prompt、上下文、模型输出、工具调用、检索结果、错误、耗时和成本。没有 trace，就很难判断问题出在检索、Prompt、模型、工具还是前端协议。

### LangSmith 类工具

LangSmith 这类工具常用于记录链路、调试 Prompt、回放样本和做评估。即使不使用具体平台，也应该借鉴它的思路：每个步骤有输入输出，每次改动可以和历史结果对比。

### RAG 评估

RAG 评估至少拆成两层：

- 检索质量：正确文档是否被召回，排名是否足够靠前。
- 生成质量：答案是否基于召回内容，是否正确引用，是否幻觉。

常用指标：

| 指标 | 关注点 |
|------|--------|
| Recall@K | 正确片段是否出现在前 K 个召回结果 |
| MRR | 第一个正确结果排名是否靠前 |
| Answer Correctness | 最终答案是否正确 |
| Faithfulness | 答案是否忠于上下文 |
| Citation Accuracy | 引用是否对应真实来源 |

### Agent 评估

Agent 评估要看任务是否完成，而不只是回答是否通顺。常见指标包括任务完成率、工具调用成功率、人工确认率、重试次数、失败原因分布和用户采纳率。

### 延迟与成本

Agent 比普通问答更容易变慢，因为它可能多轮检索、调用工具、重排和反思。优化时要拆分：

- 首 token 延迟。
- 总完成耗时。
- 工具耗时。
- 检索和重排耗时。
- token 数和模型费用。
- 失败重试带来的额外成本。

## 常见坑点

- 只看用户主观反馈，没有固定评估集，改动效果不可比较。
- 只评估最终答案，不记录召回片段，无法定位 RAG 问题。
- trace 里记录敏感信息，没有脱敏和访问控制。
- Prompt、模型版本和索引版本没有记录，问题无法复现。
- 只优化正确率，忽略延迟和成本，系统不可上线。
- 离线评估集太理想，覆盖不到真实用户的模糊问题和错误输入。
- 没有按失败原因分类，所有问题都被笼统归为“模型不稳定”。

## 面试回答模板

> 我会把 Agent 评估分成离线评估和线上观测。离线用固定问题集回放，分别看 RAG 的 Recall@K、答案正确率、引用准确率，以及 Agent 的任务完成率和工具成功率；线上记录 trace，把 prompt、检索结果、工具调用、模型输出、耗时、成本和用户反馈串起来。这样出现坏回答时可以定位是数据没召回、上下文拼错、工具失败、模型幻觉还是前端协议问题。每次改 Prompt、模型或索引，都要和历史基线对比，而不是凭感觉上线。

## 后续实战方向

- 为前端知识库 RAG 准备 30 条固定评估问题和标准来源片段。
- 给每次问答记录 prompt 版本、索引版本、topK 文档和最终引用。
- 建立 Agent 失败分类：无召回、召回错误、工具失败、输出格式错误、用户取消。
- 做一个简单评估报表，展示正确率、召回率、平均延迟和平均 token 成本。
