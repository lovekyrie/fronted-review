# Prompt / Parser / Memory

## 核心结论

Prompt 决定模型如何理解任务，Parser 决定系统如何稳定消费模型输出，Memory 决定 Agent 如何跨轮次保留上下文。三者合在一起，解决的是 Agent 从“能回答”到“能稳定执行流程”的问题。

工程上不要迷信超长 Prompt。更稳的做法是把任务目标、上下文、约束、输出 schema、工具说明和失败策略拆清楚，并用结构化 Parser 校验结果。

## 工程链路

```text
业务输入
  -> Prompt Template 注入角色、任务、上下文和约束
  -> 模型生成自然语言、JSON 或工具调用
  -> Output Parser 校验结构和字段
  -> 不合法时重试、修复或降级
  -> Memory 写入本轮摘要、用户偏好或任务状态
  -> 下一轮请求读取必要记忆
```

前端工程师需要重点关注输出能不能稳定驱动 UI。例如模型返回的是表格、步骤、表单、审批流还是图节点，都应该尽量走结构化协议，而不是让前端从自然语言里猜。

## 关键概念

### Prompt Template

Prompt Template 是可复用的提示词模板，通常包含：

- 角色：模型应该以什么身份处理问题。
- 任务：本轮要完成的具体目标。
- 上下文：用户输入、历史摘要、检索片段、工具结果。
- 约束：不能做什么、必须遵守什么边界。
- 输出格式：JSON schema、Markdown 模板或字段定义。
- 失败策略：缺信息时应该追问、拒答还是降级。

### Output Parser

Output Parser 把模型输出转换成应用可消费的数据。常见输出包括：

- JSON 对象：适合表单、配置、结构化结果。
- 分类标签：适合意图识别、路由分发。
- 步骤列表：适合任务计划和执行进度。
- 引用答案：适合 RAG 场景，要求答案绑定来源片段。

Parser 的价值在于让失败显性化。与其让脏数据进入 UI，不如在解析阶段发现字段缺失、类型错误或引用不合法，然后触发修复或重试。

### LCEL 思路

LCEL 这类链式表达思路强调把 Prompt、Model、Parser、Retriever、Tool 组合成可观察、可复用的管道。即使项目不引入 LangChain，也可以借鉴这种拆分：每一步输入输出明确，方便测试和替换。

### Memory 三策略

#### 短期上下文

直接把最近几轮对话放进上下文窗口，适合短任务。优点是简单，缺点是 token 成本高，长会话会丢失早期信息。

#### 摘要记忆

把历史对话压缩成摘要，只保留目标、约束、决策和未完成事项。适合持续任务，但摘要生成错误会污染后续回答。

#### 长期记忆

把用户偏好、项目背景、稳定事实写入数据库或向量库。适合个性化 Agent，但必须有写入审核、过期机制、隐私治理和可删除能力。

## 常见坑点

- Prompt 堆很多规则，却没有输出 schema，结果仍然不可控。
- Parser 只在成功路径写逻辑，解析失败时没有重试和降级。
- 把所有历史消息都塞回模型，成本高且噪声越来越大。
- Memory 自动写入所有内容，导致临时偏好变成长期事实。
- 摘要记忆没有保留关键约束，后续执行偏离用户目标。
- 结构化输出缺少版本号，前端协议升级时难以兼容。

## 面试回答模板

> 我会把 Prompt、Parser、Memory 当成一条稳定性链路。Prompt 负责明确任务、上下文和约束，Parser 负责把模型输出校验成前端或服务端能消费的结构，Memory 负责在跨轮任务里保留必要状态。工程上我不会只写一大段提示词，而是会定义输出 schema、解析失败策略、记忆写入规则和过期机制。这样 Agent 的回答才能进入真实业务流程，而不是停留在聊天文本。

## 后续实战方向

- 为面试题生成器设计 JSON 输出 schema，包含题目、考点、难度、追问和参考答案。
- 做一个 Parser 失败重试机制，要求模型根据校验错误修复 JSON。
- 给 Agent 增加会话摘要，把“目标、约束、已完成、待确认”写入 Memory。
- 建立 Memory 写入白名单，只允许稳定偏好和项目事实进入长期记忆。
