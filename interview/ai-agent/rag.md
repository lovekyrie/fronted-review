# RAG 工程链路

## 核心结论

RAG 的核心不是“接一个向量库”，而是把私有知识转成可检索、可引用、可评估的上下文。完整链路包括数据加载、清洗、切分、Embedding、索引、召回、重排、上下文拼接、答案生成和效果评估。

面试中要把 RAG 讲成工程系统：数据质量决定上限，检索策略决定召回，重排和上下文组织决定答案质量，评估体系决定能否持续优化。

## 工程链路

```text
原始数据
  -> Loader 读取 Markdown、PDF、网页、数据库、工单
  -> 清洗标题、导航、脚本、重复文本
  -> Splitter 按语义和长度切分 chunk
  -> Embedding 生成向量
  -> 向量库 / 倒排索引 / 图数据库 建索引
  -> Query 改写和意图识别
  -> 向量召回 + BM25 关键词召回
  -> Reranker 重排
  -> 拼接上下文和引用
  -> 模型生成答案
  -> 评估召回率、正确率、延迟和成本
```

## 关键概念

### Loader

Loader 负责把不同来源的数据读进系统。前端知识库常见来源包括 Markdown、VitePress 页面、接口文档、组件文档、FAQ、Git 提交记录和线上故障复盘。

Loader 不只是读取文件，还要保留元数据：

- 文档路径、标题、章节。
- 更新时间和版本。
- 权限范围。
- 来源 URL 或引用锚点。

### Splitter

Splitter 决定检索粒度。chunk 太大，召回内容噪声高；chunk 太小，语义不完整。工程上通常会结合 Markdown 标题、段落、代码块和最大 token 长度做切分，并保留父级标题作为上下文。

### Embedding

Embedding 把文本映射成向量，用于语义相似度检索。它适合找“意思相近”的内容，但不一定擅长精确关键词、版本号、API 名和错误码。因此生产 RAG 经常需要混合检索。

### 向量库与 Milvus

向量库负责存储向量并做相似度搜索。Milvus 是常见向量数据库之一，适合大规模向量索引、过滤和相似度查询。面试回答中可以把它定位为“向量检索基础设施”，不要把它说成 RAG 的全部。

### BM25 与混合检索

BM25 是传统关键词相关性算法，适合精确命中术语、函数名、错误码和标题。混合检索通常把向量召回和 BM25 召回合并，再统一重排，兼顾语义相似和关键词精确。

### Reranker

Reranker 对初步召回的候选片段重新排序。它通常比纯向量相似度更能判断“这个片段是否真的能回答问题”。代价是额外延迟和成本，所以要控制候选数量。

### GraphRAG

GraphRAG 会把实体、关系和文档片段组织成图，适合复杂关联问题，例如“某个模块、负责人、故障、依赖和修复方案之间是什么关系”。它不是所有知识库的默认选项，只有当关系推理明显重要时才值得引入。

## 常见坑点

- 文档没有清洗，导航、页脚、重复内容进入索引，召回质量很差。
- chunk 切分只按固定长度，破坏标题、表格和代码块语义。
- 只用向量检索，导致 API 名、错误码、专有名词命中不稳定。
- 检索结果没有来源引用，用户无法判断答案可信度。
- 上下文拼接过多，模型被噪声干扰，成本也升高。
- RAG 没有评估集，只靠人工试几条问题判断效果。
- 数据更新没有增量索引和版本管理，答案引用过期内容。

## 面试回答模板

> 我会把 RAG 拆成数据侧、检索侧和生成侧。数据侧用 Loader 读取文档并清洗，按标题和语义切 chunk，保留路径、章节、权限等元数据；检索侧用向量召回解决语义匹配，用 BM25 解决关键词和 API 名精确匹配，再通过 reranker 重排；生成侧把 top 片段带引用塞给模型，并要求答案只能基于上下文回答。最后我会用固定评估集看召回率、答案正确率、延迟和成本，而不是只凭主观体验。

## 后续实战方向

- 实现一个离线 chunk 预处理脚本，输出 `docId`、`heading`、`content`、`source`。
- 做混合检索实验，对比纯向量、纯 BM25、向量 + BM25 + reranker 的效果。
- 建立 30 条前端面试问答评估集，记录每次检索命中的来源片段。
