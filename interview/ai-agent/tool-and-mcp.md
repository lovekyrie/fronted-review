# Tool 与 MCP

## 核心结论

Tool 调用解决的是“模型如何执行外部动作”，MCP 解决的是“工具能力如何被标准化暴露和连接”。面试里不要只说 function calling，要讲清工具 schema、权限、幂等、错误处理、调用日志和前端展示。

一个稳定的 Agent 工具系统，关键不是让模型能调用更多函数，而是让每个函数的输入可校验、输出可解析、权限可控、过程可追踪、失败可恢复。

## 工程链路

```text
用户目标
  -> 模型判断是否需要工具
  -> 根据工具 schema 生成参数
  -> 运行时校验参数和权限
  -> 调用本地函数、HTTP 服务、浏览器 MCP 或跨进程服务
  -> 返回结构化结果
  -> 模型基于结果继续推理或生成最终答案
  -> 前端展示工具调用过程、结果和错误
```

前端视角通常会接触三类工具：

- 读能力：搜索文档、读取页面、查询接口、拉取仓库文件。
- 写能力：创建工单、修改配置、发起审批、提交表单。
- 交互能力：打开浏览器、点击页面、截图、上传文件、等待用户确认。

## 关键概念

### Tool Schema

Tool Schema 描述工具名称、用途、参数类型、必填字段和返回结构。模型是否能稳定调用工具，很大程度取决于 schema 是否清晰、单一、低歧义。

设计时要注意：

- 名称表达动作，例如 `searchDocs`、`getOrderDetail`、`createTicket`。
- 参数尽量结构化，不让模型拼接大段自然语言。
- 明确必填和可选字段。
- 返回结果保持稳定字段名，避免让下游再解析自然语言。

### Function Calling

Function calling 是模型输出工具调用意图和参数，真正执行通常由应用运行时完成。也就是说，模型不应该直接拥有无限权限，应用层必须做校验、鉴权、审计和副作用控制。

### MCP

MCP 可以把工具服务和模型客户端解耦。常见 MCP Server 可以暴露文件系统、Git 仓库、数据库、浏览器、设计稿、知识库或内部平台能力。Agent 客户端只要遵守协议，就能发现工具、读取资源并调用能力。

### 浏览器 MCP

浏览器 MCP 适合做页面读取、自动化操作、截图和端到端验证。它对前端工程师特别有价值，因为很多任务不是“生成答案”，而是“理解当前页面状态并执行 UI 操作”。

典型场景：

- 读取页面 DOM 和可见文本。
- 自动点击、输入、提交表单。
- 生成页面截图用于视觉校验。
- 在真实浏览器里复现用户路径。

### 跨进程工具调用

Agent 工具经常不在同一个进程里运行。比如前端 UI 调后端 API，后端再调用 MCP Server，MCP Server 再访问浏览器或数据库。跨进程调用要补齐超时、取消、重试、日志关联和错误码设计。

## 常见坑点

- 工具职责太大，一个工具同时查询、修改、发送通知，导致模型难以稳定选择。
- 参数全靠自然语言，缺少枚举、范围和格式约束。
- 写操作没有人工确认，模型误判会直接产生副作用。
- 工具返回一大段文本，模型和前端都难以消费。
- MCP Server 暴露权限过宽，没有按项目、用户或环境隔离。
- 没有 trace id，跨进程调用失败后无法还原链路。
- 工具错误直接喂给用户，没有转换成可理解的恢复建议。

## 面试回答模板

> 我会把 Tool 看成 Agent 的执行层，而不是普通函数。设计时先定义工具边界和 schema，让模型只负责选择工具和生成参数，应用运行时负责参数校验、权限判断、实际调用、日志审计和错误恢复。MCP 的价值是把工具连接标准化，比如文件、浏览器、数据库、知识库都可以通过 MCP Server 暴露能力。对于高风险写操作，我会加人工确认、幂等 key、超时重试和调用记录，避免 Agent 变成不可控的自动脚本。

## 后续实战方向

- 给知识库做一个 `searchDocs` 工具，输入关键词和范围，返回结构化文档片段。
- 用浏览器 MCP 做 VitePress 页面巡检，自动打开页面并检查标题、链接和截图。
- 设计一套工具调用卡片 UI，展示工具名称、参数、状态、耗时和结果。
- 给写操作增加二次确认和幂等 key，形成 Agent 工具安全基线。
