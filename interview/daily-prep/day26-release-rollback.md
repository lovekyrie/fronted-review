## 阅读卡点

- 静态资源带 hash 才能做到“同时存在两个版本”，是蓝绿的前提
- 灰度按用户 / 地域 / 账号分桶，不能随机，否则用户体验不一致
- 回滚要回滚**产物**而不是回滚**代码**，避免编译差异再次踩坑

## 速记卡 / 知识点

### 发布策略矩阵

| 策略 | 核心做法 | 适合场景 | 主要风险 |
|------|----------|----------|----------|
| 覆盖式发布 | 直接替换旧版本 | 个人项目、小团队低风险系统 | 出问题影响全量用户，回滚依赖版本管理 |
| 蓝绿发布 | 新旧两套环境并存，切流量 | 对稳定性要求高、切换要快 | 资源成本更高，数据状态要兼容 |
| 滚动发布 | 分批替换实例 | 多实例服务、容器平台 | 新旧版本短时间共存，接口和资源要兼容 |
| 灰度 / 金丝雀 | 少量用户先用新版本 | 大流量业务、风险可控发布 | 分桶要稳定，监控和回滚要细 |

- 回滚要回滚“已验证产物”，不是临时回滚代码重新构建；否则可能因为依赖、环境、构建参数变化引入新差异。
- 前端静态资源回滚的前提是版本化：HTML、hash 资源、镜像 tag、source map、release 号能对应起来。
- 静态资源带 hash 后可以多版本共存，旧 HTML 引用旧 JS 仍能访问，这对蓝绿、灰度和回滚都很关键。
- 灰度分桶要稳定，例如按用户 ID、租户、地域或账号 hash；随机分桶会导致用户一会新版本一会旧版本。
- 回滚触发条件要提前定义：白屏率升高、JS 错误率升高、核心接口失败、资源 404、转化率或核心业务指标异常。
- 发布不是脚本执行完成就结束，至少要有部署后验证：容器状态、首页 200、关键资源、关键路由、监控指标。
- `latest` 适合人看，不适合精准回滚；生产部署应记录 commit SHA、镜像 tag、构建号和发布时间。
- 回滚后也要观察缓存：用户可能还拿着旧 HTML、旧 service worker 或 CDN 边缘节点缓存。

## 手写 / 流程图

```text
线上事故 5 分钟回滚流程：

监控告警 / 用户反馈
  -> 确认范围：全量 / 灰度 / 单地区 / 单浏览器
  -> 判断等级：白屏、核心链路不可用、错误率异常
  -> 决策：修复来不及则立即回滚
  -> 执行：切回上一稳定镜像 tag / 静态资源版本
  -> 验证：首页、关键路由、核心接口、错误率
  -> 观察：缓存命中、CDN、旧版本用户
  -> 记录：影响面、根因、修复动作、预防项
```

## 口述题

### 1. 蓝绿 vs 灰度 vs 金丝雀怎么选？

> 回答模板：我会先看业务风险、流量规模和基础设施能力。覆盖式发布最简单，适合低风险项目，但出问题影响全量。蓝绿发布是新旧两套环境并存，通过切流量快速上线和回滚，适合稳定性要求高的系统，但成本更高。滚动发布适合多实例服务，逐批替换，但要处理新旧版本兼容。灰度或金丝雀适合大流量业务，先放少量用户或某些租户验证，再逐步扩大。前端场景还要特别关注静态资源版本、HTML 缓存、source map 和监控指标，否则切流量容易，定位问题很难。

### 2. 回滚的“最后一公里”有哪些坑？

> 回答模板：回滚最容易卡在几个细节。第一是没有可追溯产物，只知道回滚代码，不知道线上该切回哪个镜像或哪批静态资源。第二是旧资源被删了，旧 HTML 引用的 hash JS 已经 404。第三是 HTML、CDN、浏览器缓存或 service worker 还缓存着错误版本，导致回滚后用户仍然异常。第四是配置和产物不匹配，比如回滚了 JS，但运行时 `config.js` 还是新环境配置。最后是没有部署后验证和监控观察，只看到脚本成功，不知道用户是否恢复。
