## 速记卡 / 知识点

### 四层测试对比

| 层 | 粒度 | 执行时长 | 维护成本 | 典型工具 |
|----|------|----------|----------|----------|
| **单元测试** | 函数 / 类 / hook | 毫秒级 | 低 | Vitest / Jest |
| **组件测试** | 单个组件 | 秒级 | 中 | VTU / Testing Library |
| **集成测试** | 多组件 + API | 秒级 | 中高 | Vitest + MSW |
| **E2E 测试** | 完整页面流程 | 分钟级 | 高 | Playwright / Cypress |

补充层：**视觉回归**（Percy / Chromatic）—— 用截图对比检测 UI 变化。

### 测试金字塔

```text
        /\
       / E2E \        ← 少量关键路径
      /--------\
     / 集成测试  \     ← 关键页面交互
    /------------\
   / 组件测试      \   ← 复杂组件
  /----------------\
 /  单元测试         \  ← 大量纯函数 / 工具
/____________________\
```

### 每层该测什么

| 层 | 测什么 | 不测什么 |
|----|--------|----------|
| 单测 | 纯函数、工具函数、自定义 hook | 不 mock 过重、不测 DOM |
| 组件 | 渲染结果、用户交互、props/emit | 不测内部状态、不测样式细节 |
| 集成 | 页面级流程、API 联调 | 不覆盖每个分支 |
| E2E | 核心业务路径（登录/下单/支付） | 不覆盖所有排列组合 |

### 覆盖率 ≠ 质量

- 高覆盖不代表高质量：只测 happy path 也能 100% 行覆盖。
- 关注 **branch coverage**（分支覆盖）比 line coverage 更有意义。
- 覆盖率是下限指标，不是目标：80% 是通常的合理线。

## 手写 / 流程图

### 测试策略决策树

```text
新功能上线，要写什么测试？
  ├─ 有纯函数 / 工具？→ 单元测试（优先）
  ├─ 有复杂组件（表单/表格/弹窗）？→ 组件测试
  ├─ 有多组件联动 + API？→ 集成测试（MSW mock API）
  └─ 是核心业务路径？→ E2E 测试（Playwright）

维护预算有限？
  → 砍 E2E（维护成本高、flaky）
  → 保单测 + 组件测试（ROI 最高）
```

## 口述题

### 1. 测试分层怎么讲才像工程视角？

回答模板：

> 我用测试金字塔来组织：底层大量单元测试覆盖纯函数和工具，执行快、维护成本低。中间层是组件测试，关注用户可见行为——渲染、点击、输入。顶层少量 E2E 测试覆盖核心业务路径——登录、下单、支付。
>
> 关键是 **ROI 思维**：不是每层都要写很多。单测成本低收益高，优先写。E2E 成本高且容易 flaky，只覆盖 P0 路径。组件测试是性价比的甜蜜点——比单测贴近用户，比 E2E 稳定。实际项目中我会先看哪层 bug 最多，把测试预算花在那一层。

### 2. 什么代码不值得测？

回答模板：

> 四类。第一，纯 UI 展示且无逻辑的组件——比如只接收 props 渲染文字，没必要写测试，视觉回归工具更合适。第二，框架/第三方库的行为——不需要验证 Vue Router 的 push 有没有生效，那是库的责任。第三，实现细节——不测内部 state 的值，测用户看到的结果。第四，频繁变动的 UI 细节——如果一个弹窗每周改一次样式，写详细的快照测试只会带来维护负担。
>
> 核心原则：**测行为不测实现，测确定性不测易变性**。

## 5 分钟录音顺序

按这个顺序录，不要临场重新组织：

1. 测试金字塔 + 四层职责（1.5 分钟）
2. 每层该测什么 / 不该测什么 + 工具选型（2 分钟）
3. 覆盖率误区 + ROI 思维（1.5 分钟）

录完后自查：

- 是否说出四层的粒度和典型工具。
- 是否说出"测行为不测实现"。
- 是否说出覆盖率是下限不是目标。
- 是否说出 E2E 只覆盖 P0 路径。
