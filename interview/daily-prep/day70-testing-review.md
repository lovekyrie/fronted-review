## 速记卡 / 知识点

### 分层策略 3 档答题

**1 分钟版：**

> 金字塔分四层。底层大量单测（纯函数 / 工具），中间组件测试（用户行为），上层少量 E2E（核心路径）。测行为不测实现，覆盖率是下限不是目标。

**3 分钟版：**

> 在 1 分钟基础上加：工具选型（Vitest + VTU + Playwright），每层该测什么不该测什么，ROI 思维（E2E 成本高只覆盖 P0，组件测试是甜蜜点）。

**5 分钟版：**

> 在 3 分钟基础上加：CI 集成（Lighthouse CI + 覆盖率门槛 + E2E 并行），flaky test 治理四步法，真实案例（覆盖率从 X% 到 Y%）。

### Flaky 治理流程

```text
1. 识别 → CI 标记 flaky（连续 3 次有时过有时挂）
2. 分类 → 时间/顺序/异步/环境残留
3. 修复 → fake timer / 独立 setup / flushPromises / afterEach 清理
4. 预防 → CI retry 兜底 + 独立测试 + 禁真实网络
```

### CI 时长控制

| 策略 | 效果 |
|------|------|
| 单测并行（Vitest 默认） | 充分利用多核 |
| E2E 并行（workers=4） | 测试间无共享状态 |
| 增量测试（只跑变更相关） | 最大幅度减少时长 |
| 分阶段（单测先跑，E2E 后跑） | 快反馈 + 完整验证 |

## 手写 / 流程图

### 测试链路图

```text
本地开发
  ├─ Watch 模式：Vitest watch → 改代码 → 自动重跑相关测试
  └─ 手动运行：vitest run --coverage

PR 阶段
  ├─ CI 自动触发
  │   ├─ Lint + Type Check（1-2 分钟）
  │   ├─ 单测 + 组件测试（2-5 分钟）
  │   ├─ 覆盖率检查（增量 ≥ 80%）
  │   └─ E2E 测试（5-10 分钟，并行）
  └─ 全部通过 → 允许合并

预发环境
  └─ E2E 冒烟测试（核心路径）

生产环境
  └─ 线上监控（web-vitals RUM + 错误上报）
```

### 覆盖率策略

```text
全量覆盖率：整体 ≥ 80%（作为基线）
增量覆盖率：新增/修改代码 ≥ 80%（每次 PR 强制）
分支覆盖率：关注 branch coverage（比 line 更有意义）
排除项：配置文件 / 类型声明 / mock 数据 不计入覆盖率
```

## 口述题

### 1. 前端测试分层怎么讲？

回答模板：

> 我用测试金字塔来组织，四层。底层是**单元测试**——覆盖纯函数、工具函数、自定义 hook，用 Vitest 跑，毫秒级快。中间是**组件测试**——用 VTU 或 Testing Library，测用户可见行为：渲染、点击、输入、emit。再上面是**集成测试**——多组件 + API 联调，用 MSW mock API。顶层是 **E2E**——Playwright 覆盖核心业务路径，10-20 个就够。
>
> 关键原则是 **ROI 思维**：单测成本低收益高，多写；E2E 成本高易 flaky，少写只覆盖 P0。组件测试是性价比甜蜜点。覆盖率是下限不是目标——80% 的覆盖率如果全是 happy path，不如 60% 但覆盖了错误分支。

### 2. 3 道自抽追问

**Q: 你们团队覆盖率是多少？怎么推动的？**

> 我们全量覆盖率 75%，增量覆盖率要求 80%。推动方式：CI 卡增量覆盖率门槛——新代码不达标不让合并。不追求全量 100%，因为有些遗留代码补测试 ROI 太低。重点保证新增功能和 bug fix 有测试。

**Q: 你修过什么 flaky test？**

> 有一个 E2E 登录测试偶发失败。排查发现是测试间共享了同一个测试账号，并发时 session 冲突。修复方法：每个测试用 API 创建独立测试用户，测完删除。同时给 CI 加了 retry=2 作为兜底。

**Q: 单测 vs E2E 怎么选？**

> 看两个维度：**变更频率**和**故障成本**。变更频繁的逻辑（工具函数、数据处理）用单测——重构时快速验证。故障成本高的路径（支付、注册）用 E2E——保证端到端流程不断。中间地带（表单组件、列表交互）用组件测试。

## 今日复盘

最容易被击穿的 3 题：

1. "你们覆盖率多少？怎么推动？"——必须有具体数字 + 推动策略（CI 卡门槛）。
2. "你修过什么 flaky test？"——需要准备一个真实案例（原因 + 修复 + 预防）。
3. "组件测试和 E2E 的边界在哪？"——需要说出变更频率 + 故障成本两个维度。

本周新增的 3 个"为什么"：

1. 为什么 Testing Library 不提供 shallowMount？（鼓励测真实行为，不测实现细节）
2. 为什么 Vitest 比 Jest 快？（原生 ESM + Vite 按需编译 + 不需要 babel transform）
3. 为什么 E2E 测试容易 flaky？（真实浏览器 + 网络 + 动画 + 共享状态 → 不确定性多）
