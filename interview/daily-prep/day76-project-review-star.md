## 阅读卡点

- 面试官关注的是**你做了什么 + 为什么这么做 + 效果量化**
- 常见反面回答：“我们团队做了 XX” → 永远要回到“我”的动作
- Result 要带**量化**：首屏从 X 到 Y、事故率下降 Z%

## 速记卡 / 知识点

### STAR 模板

| 要素 | 说什么 | 时长 |
|------|--------|------|
| **S**ituation | 业务背景 + 痛点（一句话） | 15 秒 |
| **T**ask | 你的职责 + 目标（具体指标） | 15 秒 |
| **A**ction | 你做了什么（核心 2-3 步）| 60 秒 |
| **R**esult | 量化收益 + 后续影响 | 30 秒 |

### 量化手法

| 不好 | 好 |
|------|-----|
| "提升了性能" | "LCP 从 4.2s 降到 2.1s" |
| "减少了 bug" | "线上事故率下降 60%" |
| "提高了效率" | "构建时间从 180s 降到 45s" |
| "优化了体验" | "用户跳出率降低 15%" |

### 3 层追问预案

```text
第 1 层：你做了什么？→ STAR 正文
第 2 层：为什么这么做？→ 方案选型理由（对比了哪些方案，为什么选这个）
第 3 层：如果重来会怎么做？→ 反思 + 改进点（体现成长性）
```

### 短板承认公式

```text
"这个方向我没有直接实战经验，但我了解它属于 [X 类问题]，
常见解法是 [Y]，如果需要我愿意快速上手。"
```

## 手写 / 流程图

### 项目 STAR 示例模板

```text
项目 A：电商首页性能优化
────────────────────────────────────────
S: 电商首页 LCP P75 = 4.2s，跳出率高于行业平均，产品要求优化到 2.5s 以下
T: 作为前端负责人，主导首页性能优化，目标 LCP < 2.5s
A:
  1. 用 Lighthouse + CrUX 定位瓶颈：首屏大图未 preload，JS 280KB 阻塞渲染
  2. 图片：WebP + preload + fetchpriority="high" + CDN
  3. JS：按路由 Code Split，首屏 chunk 280KB → 90KB
  4. CSS：Critical CSS 内联，非关键 CSS async
  5. 建立 Lighthouse CI 防止劣化
R: LCP P75 降到 2.1s，跳出率降 15%，后续持续用 web-vitals RUM 监控

追问预案：
  Q: 为什么不用 SSR？→ 当时团队没有 Node 运维能力，ROI 不如静态优化
  Q: 如果重来？→ 会更早引入 Lighthouse CI，避免发版劣化
```

```text
项目 B：后台权限系统重构
────────────────────────────────────────
S: 后台权限硬编码在前端路由里，每次加角色要改代码发版，运营频繁找开发
T: 设计动态权限系统，支持运营自助配置角色和菜单
A:
  1. 设计三层权限：接口级（后端中间件）+ 路由级（动态 addRoute）+ 按钮级（v-auth 指令）
  2. 后端出权限 API，前端根据返回动态生成路由和菜单
  3. 封装 v-auth 指令 + useAuth hook，团队统一使用
  4. 补了权限相关的组件测试
R: 运营可自助配置，前端发版频率降低 40%，权限相关 bug 降低 70%

追问预案：
  Q: 菜单和路由怎么同步？→ 同一份数据源，菜单从路由配置派生
  Q: 前端权限能防攻击吗？→ 不能，只是体验兜底，后端必须校验
```

## 口述题

### 1. 介绍一个你主导的项目

STAR 稿（2 分钟版）：

> **S**：我们电商首页的 LCP P75 在 4.2 秒左右，跳出率高于行业平均。
>
> **T**：我作为前端负责人，目标是把 LCP 优化到 2.5 秒以下。
>
> **A**：第一步用 Lighthouse 和 CrUX 定位瓶颈，发现两个主要问题：首屏大图是 PNG 且没有 preload，JS bundle 有 280KB 阻塞渲染。第二步做了四件事——图片换 WebP 加 preload；按路由 Code Split 把首屏 chunk 降到 90KB；Critical CSS 内联；给 API 域名加 preconnect。第三步建了 Lighthouse CI，每次 PR 自动跑分防止劣化。
>
> **R**：LCP P75 降到 2.1 秒，跳出率降低 15%。上线后持续用 web-vitals RUM 监控。

### 2. 这个项目最难的地方是什么？

回答模板：

> 最难的是定位瓶颈而不是盲目优化。一开始团队想直接上 SSR，但我分析了 Lighthouse 报告，发现瓶颈不是 TTFB 而是资源大小和加载策略。SSR 的投入（Node 运维、改造成本）远高于静态优化。最后用成本更低的方案（Code Split + 图片优化 + preload）达到了更好的效果。
>
> 另一个难点是让优化持续生效——代码会劣化。所以我推动了 Lighthouse CI 和 Bundle Analyzer，从流程上保证每次发版性能不退化。
