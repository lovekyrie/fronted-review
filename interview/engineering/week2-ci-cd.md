### CI/CD

很多人回答 CI/CD 时会停留在“自动化构建、自动化部署”这八个字，这对高级前端面试不够。更好的回答方式是：**把 CI/CD 放进一条真实交付链路里讲清楚。**

对前端来说，这条链路通常是：

`提交代码 -> 触发工作流 -> 安装依赖 / 质量检查 -> 构建产物 -> 打镜像 -> 推送仓库 -> 部署到服务器 -> 验证与回滚`

如果你能把这条链路讲顺，再结合真实项目解释每一步的风险和取舍，答案就会明显比“概念解释”更像高级前端。

#### 1. CI 和 CD 分别解决什么问题

##### 1.1 CI：持续集成

CI 的重点不是“自动执行命令”本身，而是**尽早发现变更带来的问题**。

常见目标：

- 代码合并前先跑校验
- 统一依赖安装和构建环境
- 提前暴露 lint、测试、构建失败
- 保证主干分支尽量稳定

对前端项目来说，CI 最常见的动作是：

- 安装依赖
- 类型检查
- lint
- 单元测试 / 组件测试
- 构建校验

##### 1.2 CD：持续交付 / 持续部署

CD 的核心是把“可通过校验的产物”稳定送到目标环境。

这里通常有两种语义：

- **持续交付**：产物已经自动准备好，但是否上线还可以人工确认
- **持续部署**：通过校验后自动上线

面试中最好顺手补一句：很多团队口头上都说 CI/CD，但实际流程可能只有“自动部署”，并没有完整的“持续集成质量门禁”。

#### 2. 前端项目里的完整 CI/CD 链路

可以把它拆成 6 步。

##### 2.1 触发工作流

通常由以下事件触发：

- `push`
- `pull_request`
- tag 发布
- 手动触发

这里的设计重点不是“会不会写 YAML”，而是：**什么动作该在 PR 阶段发生，什么动作该在主干分支发生。**

##### 2.2 质量校验

这是 CI 的核心。

常见质量门禁：

- `eslint`
- `typescript`
- 单元测试
- 构建测试
- E2E 或冒烟测试

没有这一层，后面的“自动部署”更像“自动把错误送上生产”。

##### 2.3 构建产物

前端项目的构建产物通常是：

- 静态文件
- Docker 镜像
- source map

如果是纯静态站点，最终部署的可能就是一份 `dist`。如果采用容器化交付，最终更稳定的交付单元通常是镜像。

##### 2.4 推送产物

常见目标：

- Docker Registry
- 对象存储
- 静态托管平台
- 制品仓库

这一步的重点是让“本地构建结果”和“线上实际部署内容”尽量一致。

##### 2.5 部署

部署方式常见有：

- 直接把静态文件 rsync 到服务器
- 容器拉新镜像后重启
- Kubernetes 滚动更新
- 平台托管自动发布

前端岗位里，容器化部署越来越常见，因为它能把运行环境一起固化。

##### 2.6 验证与回滚

高级面试通常会追问这里。

如果部署失败或新版本有问题，需要回答：

- 怎么发现
- 怎么回滚
- 怎么减少回滚影响

没有回滚、监控、告警的部署链路是不完整的。

#### 3. 这个仓库里的真实部署链路

当前仓库已经有一条真实但仍可继续补强的流程，核心文件是：

- `.github/workflows/deploy.yml`
- `Dockerfile`
- `nginx.conf`

可以把这条链路拆成下面几步。

##### 3.1 GitHub Actions 触发

当前工作流在 `main` 和 `master` 分支 push 时触发：

```yaml
on:
  push:
    branches:
      - main
      - master
```

这说明当前策略偏“主干自动发布”，更接近持续部署。

##### 3.2 构建并推送镜像

第一阶段 `build-and-push` 会做这些事：

1. checkout 代码
2. 登录 GHCR
3. 生成镜像 tag
4. 构建并推送镜像

```yaml
- name: Build and push Docker image
  uses: docker/build-push-action@v5
  with:
    context: .
    push: true
    tags: ${{ steps.meta.outputs.tags }}
```

这里的关键点不是“用了哪个 action”，而是：**部署单元不是散落的静态文件，而是一份可重复拉取的镜像。**

##### 3.3 Dockerfile 在做什么

当前 `Dockerfile` 使用了两阶段构建：

```dockerfile
FROM node:20-alpine AS builder
...
RUN pnpm run docs:build

FROM nginx:alpine
COPY --from=builder /app/.vitepress/dist /usr/share/nginx/html
```

这个设计的好处是：

- 构建环境和运行环境分离
- 最终镜像更小
- 运行镜像里不需要 Node、pnpm 等构建依赖

对前端项目来说，这是很典型也很合理的容器化思路。

##### 3.4 Nginx 在做什么

`nginx.conf` 主要承担：

- 静态资源托管
- gzip 压缩
- 路由兜底
- 静态资源缓存

```nginx
location / {
    try_files $uri $uri.html $uri/ /index.html;
}
```

这行配置的意义是：如果当前路径没有直接命中静态资源，就回退到 `index.html`，保证前端路由或文档路由能正常工作。

##### 3.5 远程部署

第二阶段 `deploy` 通过 SSH 到服务器执行：

1. 登录镜像仓库
2. `docker pull` 最新镜像
3. 停掉旧容器
4. 删除旧容器
5. 运行新容器

```yaml
docker pull ghcr.io/${{ github.repository_owner }}/${{ env.IMAGE_NAME }}:latest
docker stop ${{ env.CONTAINER_NAME }} || true
docker rm ${{ env.CONTAINER_NAME }} || true
docker run -d \
  --name ${{ env.CONTAINER_NAME }} \
  --restart always \
  -p 8082:80 \
  ghcr.io/${{ github.repository_owner }}/${{ env.IMAGE_NAME }}:latest
```

这是一种很常见的“小团队服务器直连部署”方案，优点是实现简单、成本低、链路直观。

#### 4. 当前这条流水线的优点

##### 4.1 产物一致性较好

本地、CI 和线上最终都围绕同一份镜像交付，而不是“本地构建、服务器再手动跑一遍”。

##### 4.2 运行环境被固定

容器化之后，线上运行环境更稳定，不容易出现“本地好好的，服务器不一样”的问题。

##### 4.3 上线链路清晰

从 push 到镜像构建、再到服务器拉取部署，链路很明确，排障边界也相对清楚。

#### 5. 当前这条流水线还缺什么

这是高级面试里最容易拉开差距的部分。不是只看“现在怎么做”，而是看“你知道还缺什么”。

##### 5.1 缺少真正的 CI 质量门禁

当前工作流主要是构建和部署，还没有在部署前明确执行：

- lint
- 单元测试
- 构建前校验

这意味着它更像“自动发布流水线”，还不算完整的 CI/CD。

更合理的结构应该是：

1. `lint`
2. `test`
3. `build`
4. `build-and-push`
5. `deploy`

只有前面全通过，后面才允许继续。

##### 5.2 回滚能力比较原始

当前部署使用 `latest` 镜像，虽然也打了 `sha tag`，但部署脚本实际拉的是 `latest`。这会带来两个问题：

- 回滚时不够精确
- 很难直接定位“当前线上到底是哪一个提交对应的镜像”

更稳的做法是：

- 部署时使用 commit SHA tag
- 记录当前版本号
- 保留最近几个稳定版本
- 回滚时直接切回上一版镜像

##### 5.3 缺少部署后验证

现在部署动作完成后，没有明显的健康检查和冒烟验证。

更稳的方案包括：

- 部署后访问首页检查状态码
- 校验关键资源是否可访问
- 失败时中断并告警

##### 5.4 缺少 source map 与监控闭环

前端线上排障依赖：

- 错误监控
- source map 上传
- 版本号映射

否则用户报错后只能看到压缩代码堆栈，问题定位效率会很差。

##### 5.5 缺少环境分层

高级团队通常不会只保留一个生产环境概念，还会区分：

- 开发环境
- 测试环境
- 预发布环境
- 生产环境

这样才能让“先验证再上线”形成稳定流程。

#### 6. 前端 CI/CD 的关键设计点

##### 6.1 不要把 secrets 暴露进前端 bundle

CI/CD 会使用大量环境变量和 secrets，但要区分：

- **工作流 secrets**：给 GitHub Actions、Docker、SSH、部署脚本用
- **前端构建变量**：会进入浏览器端产物，不能当成秘密

这是很多前端同学容易混淆的地方。

##### 6.2 构建产物要可追溯

可追溯性至少包括：

- 当前线上版本对应哪个 commit
- 对应哪个镜像 tag
- 对应哪份 source map

否则线上排障会很被动。

##### 6.3 部署脚本要幂等

幂等的意思是同一部署动作重复执行，不应该让状态越来越乱。

比如当前脚本中：

```bash
docker stop ${{ env.CONTAINER_NAME }} || true
docker rm ${{ env.CONTAINER_NAME }} || true
```

这就是典型的幂等思路。即使目标容器不存在，也不会让脚本直接失败。

##### 6.4 监控和告警不是可选项

真正的交付闭环不是“脚本跑完了”，而是“用户可用了，而且一旦出问题能被及时发现”。

#### 7. 高频面试题

##### 7.1 CI 和 CD 的区别是什么

CI 关注代码集成后的质量校验和快速反馈，CD 关注通过校验后的产物如何稳定交付到目标环境。前者偏质量门禁，后者偏交付落地。

##### 7.2 前端项目为什么要容器化部署

因为它能固定构建和运行环境，提高交付一致性，也更容易通过镜像做版本管理、部署和回滚。

##### 7.3 自动部署为什么不等于完整的 CI/CD

因为如果没有 lint、测试、构建验证、健康检查和回滚策略，它只是“把发布动作自动化”，并没有形成完整质量闭环。

##### 7.4 前端部署为什么要关心回滚

因为前端发布虽然是静态资源或容器，看起来简单，但一旦发布错误版本，影响的是所有用户。没有版本化产物和快速回退能力，上线风险会很高。

##### 7.5 source map 为什么和 CI/CD 有关

因为 source map 不只是本地调试工具，它关系到线上错误定位。理想链路是构建时生成、发布时上传、监控平台按版本号匹配。

#### 8. 面试回答建议

如果被问 CI/CD，不要只按定义回答。更稳的结构是：

1. 先说 CI 和 CD 分别解决什么问题
2. 再说一条真实前端项目的交付链路
3. 再讲你们项目当前是怎么做的
4. 最后补上这条链路还缺什么，以及你会怎么改

这样答案就会从“知道名词”升级成“能负责真实交付流程”。
