### 模块化

模块化不是把文件拆开这么简单，它解决的是三个问题：

- **作用域隔离**：避免全局污染
- **依赖管理**：明确谁依赖谁
- **可组合与可复用**：让大型应用能被拆成可维护单元

高级面试里的重点不在于死记 AMD、CMD 的定义，而在于你是否理解：

- 为什么现代工程基本都围绕 ESM 展开
- 模块系统和构建工具之间是什么关系
- tree-shaking、代码分割、循环依赖为什么都和模块模型有关

#### 1. 常见模块方案

##### 1.1 CommonJS

Node.js 传统模块系统，核心是运行时加载。

```js
// math.js
const add = (a, b) => a + b

module.exports = {
  add,
}

// main.js
const math = require('./math')
console.log(math.add(1, 2))
```

特点：

- 同步加载
- 导出的是值对象
- 更适合服务端和早期 Node 生态
- 静态分析能力弱于 ESM

##### 1.2 AMD / CMD

这是浏览器原生模块能力不成熟时的历史方案，现在更多是“知道它存在和解决过什么问题”。

- AMD 强调依赖前置、异步加载
- CMD 强调就近依赖

现代前端面试中一般不会把它们作为重点深挖，但你要知道它们出现的背景：**浏览器端也需要模块化，只是当时还没有原生 ESM。**

##### 1.3 ES Modules

现代前端工程的主流模块系统。

```js
// math.js
export const add = (a, b) => a + b

// main.js
import { add } from './math.js'
console.log(add(1, 2))
```

ESM 的关键价值不是语法更好看，而是：

- 依赖关系是静态声明的
- 构建工具更容易做分析和优化
- 浏览器和 Node 都在逐步统一到这套语义

#### 2. ESM 和 CommonJS 的核心差异

##### 2.1 静态 vs 运行时

ESM：

- `import` / `export` 在语法层就是模块边界
- 构建阶段能提前知道依赖图

CommonJS：

- `require()` 是函数调用
- 可以出现在条件、分支、运行时路径中

这就是为什么 tree-shaking 对 ESM 更友好。

##### 2.2 值的绑定方式

ESM 导出的是**实时绑定**，导入方拿到的是对导出绑定的引用。

CommonJS 更接近“导出一个对象快照，然后由 `require()` 拿到这个对象”。

这会直接影响循环依赖时的行为理解。

##### 2.3 加载时机

- CommonJS 更偏同步加载，天然适合 Node 的本地文件系统场景
- ESM 在设计上更适合静态分析和异步化加载模型

#### 3. 为什么模块系统和构建工具强相关

构建工具不是凭空工作的，它必须建立在模块语义之上。

例如构建器要回答这些问题：

- 哪些文件是入口
- 哪些代码最终被引用
- 哪些依赖可以拆到异步 chunk
- 哪些导出根本没被使用

如果模块系统越清晰、越静态，这些问题就越容易在构建阶段被回答。

#### 4. tree-shaking 为什么依赖 ESM

tree-shaking 的本质是：**把没有被使用的导出从最终产物中移除。**

想做到这一点，构建器必须提前知道：

- 模块导出了什么
- 其他模块使用了什么
- 某段导入是否可能在运行时才决定

ESM 更适合这件事，因为：

- 导入导出是静态语法
- 导入路径通常在编译期可知
- 不需要先执行模块才能知道依赖关系

但要注意：**用了 ESM 不代表 tree-shaking 一定有效。**

常见失效原因：

- 依赖包仍然是 CommonJS
- 模块包含明显副作用
- `sideEffects` 标记不准确
- 导入方式不利于优化

#### 5. 动态 `import()` 的意义

动态 `import()` 不只是语法糖，它给了构建器一个天然的异步边界。

```js
button.addEventListener('click', async () => {
  const { openDialog } = await import('./dialog.js')
  openDialog()
})
```

这通常意味着：

- 这部分代码不必进入首屏主包
- 可以在运行时按需下载
- 构建器可以据此拆出独立 chunk

所以动态 `import()` 和代码分割强相关。

#### 6. 循环依赖为什么难

循环依赖不是单纯“坏代码”，而是需要你理解模块初始化顺序。

例如：

- A 引用 B
- B 又引用 A

CommonJS 下更常见的问题是拿到“未完成初始化的导出对象”。

ESM 下虽然语义更严格，但如果你在模块初始化阶段就依赖尚未完成的绑定，也一样会踩坑。

面试里更好的回答方式是：

- 先说循环依赖本质上是初始化时序问题
- 再说不同模块系统在表现上的差异
- 最后说工程里如何规避：拆职责、抽公共层、减少顶层执行副作用

#### 7. Babel、bundler、模块系统三者关系

这三者经常被混在一起，实际上不是一层问题。

##### 7.1 模块系统

定义代码怎样导入导出，比如 ESM 和 CommonJS。

##### 7.2 Babel

负责代码转换，比如：

- 新语法降级
- JSX 转换
- AST 层面的插件处理

它本身不是完整的 bundler。

##### 7.3 bundler

负责从入口出发组织整张依赖图，最后输出可运行产物，比如 webpack、Rollup、Vite 的 build 阶段。

高级面试里，一个常见误区是把“Babel 编译项目”说成“Babel 打包项目”。这在概念上是错位的。

#### 8. 真实项目里怎么用模块化

##### 8.1 优先使用 ESM

现代前端项目默认优先选择 ESM，这是构建优化、静态分析和生态统一的基础。

当前仓库根目录的 [package.json](/Users/duanyupeng/project/study/fronted-review/package.json) 里已经设置了：

```json
{
  "type": "module"
}
```

这意味着该项目默认按 ESM 语义处理 `.js` 文件。

##### 8.2 让模块边界清晰

比起“文件数量多”，更重要的是“依赖方向清楚”：

- UI 组件不要反向依赖页面层
- `utils` 不要偷偷依赖业务状态
- 顶层模块避免隐式副作用

##### 8.3 控制模块副作用

如果模块一被导入就执行大量逻辑，会带来：

- tree-shaking 效果下降
- 测试困难
- 循环依赖更难排查

##### 8.4 善用动态导入

动态导入适合：

- 路由级页面
- 体积大的编辑器、图表库
- 低频使用功能

不适合滥用到细碎到反而造成网络开销失衡的程度。

#### 9. 高频面试题

##### 9.1 CommonJS 和 ESM 的核心区别是什么

CommonJS 偏运行时加载，`require()` 可以动态执行；ESM 的导入导出是静态声明，更利于构建阶段分析和优化。

##### 9.2 为什么 tree-shaking 更依赖 ESM

因为构建器只有在编译阶段就确定依赖边界时，才能安全移除未使用代码。ESM 的静态结构天然更适合这件事。

##### 9.3 动态 `import()` 为什么能帮助拆包

因为它建立了异步边界，构建器可以把相关依赖图切出去，在运行时再按需加载。

##### 9.4 为什么循环依赖难排查

因为问题不只在“谁依赖谁”，更在“谁先初始化、谁先读取对方导出”。本质是模块初始化时序问题。

##### 9.5 Babel 和模块系统是什么关系

Babel 可以转换模块语法，也可以转换其他语法，但它不等于模块系统本身。模块系统定义的是导入导出的语义，Babel 是转换工具。

#### 10. 面试回答建议

被问模块化时，不要只按历史时间线背名词。更稳的顺序是：

1. 先说模块化解决什么问题
2. 再说 ESM 与 CommonJS 的机制差异
3. 再说为什么这会影响 tree-shaking、代码分割和循环依赖
4. 最后落到真实工程里的模块边界设计

这样答案才会从“知道概念”升级成“理解工程含义”。
