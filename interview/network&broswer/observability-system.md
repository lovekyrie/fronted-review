# 前端可观测性系统

高级前端面试里的“监控体系”如果只讲错误上报，通常不够。更完整的表达应该是：

`发布版本 -> 指标采集 -> 日志与错误聚合 -> 告警 -> 排障 -> 回滚 -> 复盘`

也就是说，可观测性不是单个 SDK，而是一套帮助团队理解线上状态的系统。

## 一、为什么前端需要可观测性系统

前端线上问题有几个天然难点：

- 用户环境复杂
- 代码已经压缩混淆
- 问题往往只在特定浏览器、设备、网络下出现
- 很多问题不能本地稳定复现

所以单靠用户截图和本地猜测是远远不够的。

## 二、前端可观测性通常包含什么

至少包含四层：

1. **错误监控**
2. **性能监控**
3. **行为与业务埋点**
4. **发布版本与告警系统**

真正能用于治理的系统，通常要把这四层串起来，而不是各自孤立。

## 三、错误监控层

错误监控负责回答：

- 有没有错误
- 哪类错误在增长
- 哪个版本引入的
- 影响了多少用户

常见采集源：

- `window.onerror`
- `unhandledrejection`
- 资源加载错误
- 框架错误边界
- 自定义业务异常

但错误监控不是“采到就完了”，还要补：

- 去重
- 采样
- 版本标识
- 用户上下文
- Source Map 还原

## 四、性能监控层

性能监控负责回答：

- 用户看到内容快不快
- 操作后有没有及时反馈
- 页面会不会跳
- 某次发布后性能有没有退化

常见指标：

- LCP
- INP
- CLS
- FCP
- TTFB
- 自定义业务指标

性能监控最重要的不是只看均值，而是：

- 按页面拆分
- 按设备拆分
- 按网络拆分
- 按发布版本拆分

## 五、行为与业务埋点

行为埋点负责回答：

- 用户走了哪条路径
- 哪个交互点流失高
- 某问题是否影响核心转化

这层经常被低估，但在高级前端语境里很关键，因为没有业务埋点，你很难判断一个错误或性能问题到底影响多大。

## 六、版本与发布关联

这是“治理闭环”的关键层。

监控系统必须能回答：

- 当前线上是什么版本
- 某个错误属于哪个 release
- 某次性能回退从哪个版本开始
- 某条 Source Map 对应哪个产物

如果版本标识缺失，监控数据再多，排障效率也会很差。

## 七、告警系统的设计重点

不是所有事件都值得通知人。

更合理的告警维度包括：

- 错误率是否突增
- 是否发生在新发布窗口
- 是否集中在高价值页面
- 是否影响核心链路
- 是否伴随性能指标退化

告警设计的目标不是“多报”，而是“报得准”。

## 八、排障闭环

一套可观测性系统的价值，最终体现在排障闭环上。

更完整的链路是：

1. 发现异常
2. 聚合异常
3. 关联版本
4. 结合 Source Map / 页面 / 用户环境定位
5. 判断是否需要热修或回滚
6. 验证恢复情况
7. 复盘并补监控

如果只做到“看到了错误”，还谈不上真正的线上治理。

## 九、前端可观测性最常见的缺口

高级面试里，可以主动指出这些常见缺口：

- 只有错误监控，没有性能监控
- 有监控，没有 release 关联
- 有埋点，没有告警
- 有告警，没有分级
- 有数据，没有排障流程
- 监控系统本身影响业务性能

这类主动识别缺口的能力，比只会列工具名更有 senior 感。

## 十、项目里怎么回答这类题

更好的答法不是“我们接了 Sentry 和 web-vitals”，而是：

1. 我们采哪些信号
2. 这些信号如何关联版本
3. 告警如何分级
4. 发布后如何观察
5. 出问题后如何回滚和复盘
