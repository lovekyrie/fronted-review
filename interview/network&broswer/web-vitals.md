# Web Vitals 核心指标

高级前端面试里的 Web Vitals，重点不是背定义，而是回答这三件事：

1. 它们分别反映什么体验问题
2. 如何在线上采集和分析
3. 出问题后怎么定位和优化

如果只会说“LCP、CLS、INP 很重要”，深度通常不够。

## 一、Web Vitals 解决什么问题

传统性能讨论里，很多指标更偏技术视角，比如总加载时间、请求数、脚本大小。但用户真正感受到的是：

- 页面什么时候主要内容可见
- 操作后多久有反馈
- 页面会不会在加载中乱跳

Web Vitals 就是在尽量把这些用户感知量化。

## 二、核心指标

### 1. LCP

`LCP` 表示最大内容元素完成渲染的时间。

常见 LCP 元素：

- 首屏大图
- 主标题
- 首屏 hero 区块

它反映的是：**用户多久能看到页面最主要的内容。**

### 2. INP

`INP` 表示用户交互到下一次视觉反馈之间的延迟。

它更关注真实交互体验，而不是单纯点击事件有没有触发。

它反映的是：**用户操作后页面多久“有反应”。**

### 3. CLS

`CLS` 表示页面加载和交互过程中累计布局偏移程度。

它反映的是：**页面稳不稳，会不会跳。**

典型问题：

- 图片没有预留尺寸
- 广告位异步插入
- 字体加载后重排

## 三、不要把 Web Vitals 当成实验室专用指标

Lighthouse、DevTools 能给你实验室数据，但高级面试通常会继续追问：

- 线上真实用户数据怎么采
- 怎么按设备、页面、版本分组
- 怎么和发布版本关联

也就是说，真正有治理价值的是 RUM。

## 四、如何采集

常见做法是用 `web-vitals` 库采集真实用户数据。

```ts
import { onLCP, onCLS, onINP } from 'web-vitals'

onLCP(metric => report(metric))
onCLS(metric => report(metric))
onINP(metric => report(metric))
```

一个更完整的上报载荷通常还要包含：

- 页面 URL
- 路由名
- 设备信息
- 网络类型
- release/version
- 用户或匿名 session id

否则你只能看到一组全站平均值，很难用于定位。

## 五、指标要结合场景看

不是所有页面都一样。

- 内容型页面更看 LCP 和 CLS
- 交互型后台更看 INP
- 弱网用户更容易暴露 TTFB 和资源加载问题

高级面试里更好的说法是：**不要只看全站平均值，要按页面类型、设备、网络、版本拆开。**

## 六、LCP 出问题时怎么定位

常见来源：

- TTFB 太高
- 首屏大图过大
- 关键资源加载晚
- 首屏 JS 阻塞渲染
- CSR 首屏依赖大量 JS 初始化

定位时通常先看：

1. 是服务端返回慢，还是浏览器下载慢
2. LCP 元素到底是什么
3. 它什么时候开始请求，什么时候渲染出来

常见优化动作：

- 优化首屏图尺寸和格式
- `preload` LCP 资源
- 减少阻塞脚本
- SSR / SSG 或分离关键渲染路径
- 更合理的缓存和 CDN 策略

## 七、INP 出问题时怎么定位

INP 差通常说明：

- 事件处理函数太重
- 主线程有长任务
- 一次交互触发大面积重渲染
- 布局和绘制开销过大

定位时常看：

- Performance 面板里的长任务
- 交互前后主线程火焰图
- 是否有大列表、图表、复杂组件一起更新

常见优化动作：

- 拆分长任务
- 使用 Worker
- 输入态和重计算解耦
- transition / deferred value / 虚拟列表
- 避免不必要的状态传播

## 八、CLS 出问题时怎么定位

CLS 差通常意味着页面结构在“后补内容”。

常见来源：

- 图片无宽高
- 广告位异步插入
- 动态 banner 顶部插入
- 字体切换造成重排

常见优化动作：

- 预留尺寸
- 使用骨架屏或占位容器
- 避免在已有内容上方插入元素
- 合理设置字体加载策略

## 九、Web Vitals 和监控体系怎么联动

单看指标还不够，真正的治理闭环通常是：

`采集 -> 聚合 -> 按版本分组 -> 阈值告警 -> 结合错误/发布记录定位 -> 优化 -> 验证`

例如：

- 新版本发布后 LCP 明显上升
- 同时错误监控里资源 404 增多
- 可以快速怀疑静态资源策略或 CDN 配置有问题

所以 Web Vitals 最好不是孤立模块，而应并入可观测性系统。

## 十、高级面试常见追问

### Q1：为什么现在更强调 INP 而不是 FID？

因为 FID 主要看首次输入的延迟，覆盖面有限；INP 更关注整体交互体验，更接近用户真实操作感受。

### Q2：LCP 为什么不只是“图片慢”？

因为它可能受 TTFB、阻塞资源、JS 初始化、渲染策略等多层因素影响。图片只是最常见表象。

### Q3：CLS 为什么对业务影响大？

因为页面跳动会直接影响点击准确性和使用信任感，尤其在内容页、表单页、广告页里影响明显。

### Q4：为什么不能只看实验室数据？

因为实验室数据很难覆盖真实用户设备、网络、浏览器和复杂场景。真正的发布治理要依赖线上 RUM。

## 十一、面试回答建议

如果被问 Web Vitals，不要按“定义背诵”回答。更稳的结构是：

1. 先说三个核心指标分别代表什么体验问题
2. 再说如何线上采集和按版本聚合
3. 再说不同指标出问题时的定位路径
4. 最后补一条项目里的优化案例

这样答案会从“知道指标名词”升级成“会做性能治理”。
