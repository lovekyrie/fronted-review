### 前端性能优化

高级前端面试里的性能优化，不能只回答“图片压缩、懒加载、代码分割”。更好的回答方式是：

1. 先说你关注哪些指标
2. 再说如何定位瓶颈
3. 最后说针对不同瓶颈如何做优化和取舍

也就是说，性能优化不是“背优化清单”，而是要建立这条链路：

`指标异常 -> 采集数据 -> 定位瓶颈 -> 选择优化手段 -> 验证收益 -> 持续监控`

#### 1. 性能优化先看什么指标

如果没有指标，所谓优化很容易变成主观感觉。

##### 1.1 Core Web Vitals

现代前端面试里最常被问的是这三个指标：

- `LCP`：Largest Contentful Paint，最大内容绘制时间
- `INP`：Interaction to Next Paint，交互到下一次绘制的延迟
- `CLS`：Cumulative Layout Shift，累计布局偏移

可以粗略理解成：

- LCP 看“首屏主要内容多久出来”
- INP 看“用户操作后页面多久有反馈”
- CLS 看“页面会不会乱跳”

##### 1.2 其他常见指标

- `FCP`：First Contentful Paint，首次内容绘制
- `TTFB`：Time to First Byte，首字节时间
- `TBT`：Total Blocking Time，总阻塞时间
- 自定义业务指标：搜索结果首屏时间、首个可点击时间、首个图表渲染时间

高级面试里更好的说法不是“指标越多越好”，而是：**不同页面、不同业务场景，关键指标不同。内容型页面更看 LCP，交互密集型页面更看 INP。**

#### 2. 性能问题先怎么定位

优化前先定位，不然很容易做错方向。

##### 2.1 先区分是哪一层慢

可以先粗分成四类：

1. **网络慢**：请求太多、资源太大、缓存差、CDN 不佳
2. **解析和执行慢**：JS 体积大、主线程任务长、初始化成本高
3. **渲染慢**：样式计算、布局、绘制、合成成本高
4. **交互慢**：事件处理重、状态更新链路长、渲染阻塞输入

##### 2.2 常用定位工具

- Chrome DevTools Performance
- Network 面板
- Lighthouse
- PerformanceObserver
- Web Vitals 采集
- 错误监控与 RUM 平台

面试里不要只说“我会用 Lighthouse”。Lighthouse 更适合做基线检查，复杂性能问题通常还是要回到：

- 请求瀑布
- 主线程火焰图
- 长任务
- 布局偏移来源
- 真实用户采样数据

#### 3. 从浏览器渲染链路理解性能

浏览器展示页面大致要经过：

`HTML 解析 -> DOM -> CSSOM -> Render Tree -> Layout -> Paint -> Composite`

这条链路决定了很多优化动作为什么有效。

##### 3.1 Layout / Reflow

当元素尺寸、位置变化时，浏览器可能需要重新计算布局。

容易触发的问题包括：

- 频繁改 `width`、`height`、`top`、`left`
- 读写布局信息交替发生，造成 layout thrashing
- 大量节点整体重排

```js
const width = element.offsetWidth
element.style.width = `${width + 10}px`
```

如果这种读写发生在循环里，性能会很差。

##### 3.2 Paint

布局完成后，浏览器还要把像素画出来。

高成本场景包括：

- 大面积阴影、模糊
- 复杂渐变
- 大量图片叠加
- 高频颜色或背景变化

##### 3.3 Composite

有些动画可以只走合成阶段，不重新布局或重绘整页。

通常更适合动画的属性是：

- `transform`
- `opacity`

这就是为什么动画优化里常说“尽量用 transform，而不是 top/left”。

#### 4. 首屏加载优化

##### 4.1 网络层

首屏慢时，先看资源加载链路：

- 是否有过多串行请求
- 首屏 JS / CSS 是否过大
- 图片是否过大
- 是否命中 CDN
- 是否正确使用压缩

常见动作：

- 开启 gzip / brotli
- 图片压缩与现代格式
- CDN 分发
- 减少首屏关键请求数
- `preconnect` / `preload`

```html
<link rel="preconnect" href="https://api.example.com">
<link rel="preload" href="/assets/critical.css" as="style">
```

##### 4.2 代码层

很多首屏慢，本质上是 JS 初始化太重。

常见问题：

- 主 bundle 太大
- 路由未拆包
- 大型组件首屏就加载
- 图表、编辑器、SDK 提前初始化

常见动作：

- 路由级代码分割
- 低频模块动态导入
- 延迟初始化非关键功能
- 拆出 vendor 和异步 chunk

```js
const Editor = lazy(() => import('./Editor'))
```

##### 4.3 SSR / SSG / CSR 的取舍

首屏性能经常和渲染策略有关。

- `CSR`：前端完全渲染，交互模型简单，但首屏依赖 JS
- `SSR`：首屏 HTML 更快可见，但服务端成本更高，hydration 更复杂
- `SSG`：适合文档、营销页、内容页

高级面试里更好的回答方式是：**不是所有页面都该 SSR，而是看页面是否重 SEO、重首屏、重实时交互。**

#### 5. 交互性能优化

这是现在比单纯首屏更容易拉开差距的部分。

##### 5.1 INP 为什么变差

常见原因：

- 点击后主线程有长任务
- 事件处理器里做了重计算
- 一次交互触发大面积状态更新
- 大列表重新渲染
- 布局和绘制成本太高

##### 5.2 常见优化动作

- 拆分长任务
- 使用 `requestIdleCallback` / `scheduler` 思路延后非关键任务
- 防抖 / 节流
- 虚拟列表
- 把输入态和重计算结果解耦
- 使用 React transition / deferred value 或 Vue 合理调度

```js
function debounce(fn, delay) {
  let timer = null

  return function (...args) {
    clearTimeout(timer)
    timer = setTimeout(() => fn.apply(this, args), delay)
  }
}
```

##### 5.3 长任务

超过约 50ms 的主线程任务会明显影响交互体验。

如果一个点击后要做很多计算，常见优化方式：

- 分片执行
- Web Worker
- 减少同步阻塞逻辑

```js
const worker = new Worker('worker.js')
worker.postMessage(largeData)
worker.onmessage = (event) => {
  renderChart(event.data)
}
```

#### 6. 大列表和复杂 UI

##### 6.1 列表渲染

大列表常见问题：

- DOM 节点太多
- 每次筛选或排序都全量重渲染
- 每项都绑定复杂事件和样式计算

优化方式：

- 虚拟列表
- 分页或分块加载
- 稳定 key
- 减少单项组件开销

##### 6.2 避免无意义渲染

不管是 React 还是 Vue，本质都一样：

- 切断不必要的依赖传播
- 减少无关组件重渲染
- 把状态放在合适层级

高级面试里可以直接说：性能优化很多时候不是“再加一个 memo”，而是“先把数据流设计对”。状态边界错了，所有优化都只是补丁。

#### 7. 图片与媒体优化

图片经常是内容型页面 LCP 的关键来源。

常见动作：

- 压缩图片
- 使用 WebP / AVIF
- 为不同尺寸提供不同资源
- 懒加载非首屏图片
- 提前加载首屏 hero 图
- 固定尺寸，避免布局偏移

```html
<img
  src="/banner.webp"
  width="1200"
  height="600"
  loading="lazy"
  alt="banner"
>
```

注意：

- 首屏关键图不一定适合懒加载
- 没有宽高的图片很容易导致 CLS

#### 8. 缓存策略和版本化

性能优化不能只看第一次访问，还要看回访。

##### 8.1 静态资源长缓存

对于带 hash 的静态资源，通常可以使用长缓存：

```http
Cache-Control: public, max-age=31536000, immutable
```

前提是文件名随内容变化而变化，例如：

- `app.8f3e2d.js`
- `vendor.a1b2c3.css`

##### 8.2 HTML 不应长期强缓存

入口 HTML 通常承载最新资源引用，通常更适合：

```http
Cache-Control: no-cache
```

让浏览器每次验证 HTML 是否更新，再去决定是否拉新资源。

##### 8.3 Service Worker

Service Worker 能做离线缓存、请求拦截和更灵活的缓存策略，但也会带来更新复杂度：

- 旧缓存清理
- 激活时机
- 资源版本一致性
- 调试复杂度

所以高级回答里不要无脑说“上 Service Worker 就行”。它是能力，不是默认最优解。

#### 9. CLS 和布局稳定性

CLS 差通常不是因为“慢”，而是因为页面元素在加载过程中不断跳动。

常见来源：

- 图片没有预留尺寸
- 广告位、异步模块后插入内容
- 字体切换导致文字重排
- 动态插入 banner 或提示条

优化动作：

- 给图片和容器明确宽高或纵横比
- 为异步内容预留骨架位置
- 避免在已有内容上方突然插入元素
- 谨慎使用 web font，配置合理的回退策略

#### 10. 如何回答“你做过哪些性能优化”

高级面试不看你列多少名词，而看你能不能讲成闭环。

更好的回答结构：

1. 先说场景：什么页面、什么业务、什么指标异常
2. 再说定位：通过什么数据发现问题
3. 再说动作：网络、渲染、代码、缓存分别怎么改
4. 最后说结果：指标改善多少，有没有副作用和取舍

例如：

- 首屏 LCP 从 `4.8s` 降到 `2.6s`
- 主 bundle 从 `1.2MB` 降到 `420KB`
- 搜索交互的长任务从 `180ms` 降到 `40ms`

这种回答比“我做了懒加载、压缩图片、用了缓存”更有说服力。

#### 11. 高频面试题

##### 11.1 首屏慢怎么排查

先区分是 TTFB、资源加载、JS 执行还是渲染慢，再结合 Network、Performance、Lighthouse 和真实用户监控判断瓶颈，不要上来就直接做代码分割。

##### 11.2 为什么 `transform` 动画通常比 `top/left` 更稳

因为 `transform` 更容易停留在合成阶段，而 `top/left` 往往会触发布局和重绘。

##### 11.3 为什么图片经常影响 LCP

因为很多页面的最大内容元素就是首屏大图或大标题区域。如果图片体积大、加载晚、没有 preload 或 CDN 命中差，LCP 就会很差。

##### 11.4 为什么说深度性能优化离不开数据流设计

因为很多渲染问题本质是状态边界错误、无关组件更新、计算链路过长。只靠 memo 或缓存无法根治数据流层面的浪费。

##### 11.5 性能优化和安全、可维护性会冲突吗

会。比如过度内联资源可能损害缓存策略，过度压缩或异步化可能增加调试成本，Service Worker 可能让版本管理更复杂。高级前端要能讲清楚这些取舍。

#### 12. 面试回答建议

如果被问性能优化，不要按“资源、网络、渲染”死背。更稳的顺序是：

1. 先说你看哪些指标
2. 再说你怎么定位问题
3. 再说针对不同瓶颈的优化动作
4. 最后结合一条真实链路讲收益和取舍

这样答案会从“懂一些优化技巧”升级成“能系统做性能治理”。
